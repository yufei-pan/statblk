# Lessons: full entries

entry: read that first, and look entries up here by date and name rather than reading this whole. New
entries go last, in the same commit as the change:

```markdown

```

## 2026-11-14 statblk 1.62: a copy you carry is no requirement
- Changed: statblk's package metadata requires no multiCMD (`install_requires` drops `multiCMD>=1.56`). statblk runs the multiCMD it embeds (1.67 in 1.62) wherever the installed one is older than that copy, missing, or does not import, and an installed one at least as new, as before.
- Why we had to change: the floor (1.56) was below the copy statblk uses (1.61 in 1.61), so the requirement guaranteed nothing statblk relied on; it only made pip install or upgrade a multiCMD that statblk then passed over. And pip 9.0.3 (stock on EL7 and EL8) upgrades every requirement under `-U`, which stopped the install: with multiCMD 1.55 or 1.57 installed, `pip install -U statblk==1.61` exited 2 with `configparser.DuplicateOptionError` (those versions' `mcmd`, `multicmd` and `multiCMD` entry points, which pip 9 reads as one name). Without the requirement, pip 9.0.3 upgrades 1.61 to 1.62 there (exit 0, multiCMD left as it was, statblk running its embedded 1.67), and with multiCMD 1.67 installed statblk imports that one (the CI's python:3.6 image, 2026-11-14). hpcp dropped its requirement for the same reason in 9.89; the user chose "Drop it, as hpcp did (Recommended)".
- Original design was wrong because: the requirement dates from when statblk needed an installed multiCMD; once statblk carried its own copy and chose between the two by version at import, it stated no need, and a requirement that states no need still hands the installer's own failures to every install.
- Lesson: declare as a requirement only what the program needs from outside it. A library it carries a copy of and picks by version at import is not one.

## 2026-11-14 statblk 1.62: a source the timeout cut is named, and a check it hid is unknown
- Changed: `get_macos_diskutil_info()`, `parseMount()` and `get_drives_info()` take `cut`, a list that gets the name of each command `--timeout` stopped before it finished: `diskutil` and `mount` on macOS (multiCMD's return code 124), `lsblk` on Linux (124, or still running at the refresh's deadline, when a column it fills without a full fallback is collected). `main()` prints one line per command on stderr, after the table or JSON, once per run in `-w`: what stopped it and what it leaves missing (`CUT_WHAT`). In `--check`, a cut makes a run with no problem unknown (exit 3) where it can hide what the check reads, by blanking a cell it fills (`mount`: FSUSE%) or dropping a row it decides, with the row's columns: `mount`'s list with `-M` (FSUSE% and SMART), `diskutil`'s SIZE and, with `-F`, `lsblk`'s FSTYPE (SMART only, since an unmounted row has no FSUSE%; `-M` drops those rows anyway), and each of the three with a pattern that is not `-D`; any other cut does not count. In `--check` the lines are printed only when the run exits 1 or 3, so a healthy `--check` stays silent as in 1.61 (a plain run prints them every time).
- Why we had to change: 1.61 read the output of `diskutil info -all` and macOS's `mount` and dropped their exit status, so a command cut by `-t` left columns, or whole rows, blank, with nothing on stderr and exit 0. `statblk --check` then printed nothing and exited 0, which reads as healthy: the filesystems `mount` did not list were never checked, and on macOS an unmounted disk has its SIZE only from `diskutil`, so one `diskutil` stopped before it was dropped, with its SMART, before the check judged it. On the test Mac `-t 0.5` blanks MODEL on five rows. Found by the 1.61 final review and deferred to 1.62; `lsblk`'s join at the deadline had the same silence on Linux.
- Original design was wrong because: it treated a command's output as its answer, and a cut answer is not a short one; `--check`'s exit 3 existed so that "not checked" never looks like "healthy", but only SMART fed it.
- Lesson: read the exit status of every command whose output fills the result; name a source that was cut short where the operator reads, with what it leaves missing, and let a health check count what the cut could hide from it as "could not tell", while a cut that hides nothing it reads leaves a healthy run's answer and silence as they were.

## 2026-11-16 statblk 1.63: a filter drops a row only on a value that was read
- Changed: `get_drives_info()` no longer drops a row on a value it never read, in the cases below (1.64 finished it: a source that failed without being stopped, and a Linux size or stat that reads as 0, still hid a row). On macOS a device `diskutil` gave no size is listed with SIZE blank (a size read as 0 still hides it); `-F` drops an unmounted device for a blank FSTYPE only when that type's source answered in full (Linux: `lsblk` exited 0; macOS: `diskutil` exited 0, `mount` was not stopped, and `diskutil` described the device); `-A` drops nothing on macOS, where throughput is never read; a mount whose `statvfs` fails keeps its row with SIZE blank and FSUSE% `ERROR` (as a hang shows `TIMEOUT`), which `--check` counts as unknown. `--check`'s rule for a command `--timeout` stopped, in `main()`, shrinks from a table of what each command can hide to two terms: `mount`'s list of mounted filesystems (FSUSE%, and with `-M` the rows), and a pattern (not `-D`), which can match any cell a stopped command fills.
- Why we had to change: the 1.62 rule predicted in `main()`, from the flags, which rows `get_drives_info()` would drop when a command was stopped. Each review of it found one more drop the prediction missed (a zero size, a blank FSTYPE, a mounted row falling to the unmounted branch, `-o` naming no `diskutil` column), and the same drops hid a failing disk from `--check` with exit 0 when nothing was stopped at all. Run on the real `main()` with faked commands (41 cases, and the test Mac's own output stopped after each of its lines), every failing disk 1.62 hid by a value it never read now exits 1 in those cases (the exceptions: a whole disk of size 0, a known limitation, and `-M` with a stopped `mount`, which exits 3; 1.64 closed the other places where a source that failed without being stopped, or a size read as 0, still hid a row), a healthy run with a stopped `diskutil`, or a stopped `lsblk` with `-F`, exits 0 where 1.62 gave 3, and no case moves from 1. A 0 can become 3: a disk 1.62 did not list is now judged, and exits 3 when its SMART cannot be read.
- Original design was wrong because: a value that was never read (`diskutil` not run, stopped, or silent on a device; `lsblk` missing or stopped) was taken as 0 or blank, and a filter dropped the row on it. The cut table was then a second code path guessing those drops, and it could only fall behind the first.
- Lesson: a filter drops a row only on a value that was read; a value whose source did not answer keeps the row, its cell blank. A check over the rows then needs no second path predicting what the filters hid, beyond the two facts the rows cannot show (what `mount` listed, and what a pattern would have matched in a cell a stopped command fills). 1.63 applies it to a stopped or missing command and to `statvfs`; 1.64 finished it.

## 2026-11-20 statblk 1.64: not answering is one state, whatever the cause
- Changed: `get_drives_info()` keeps one record, `unanswered`, of each command that did not answer in full (`lsblk`, macOS's `diskutil` and `mount`), with its exit status: 124 stopped by `--timeout` (or still running at the deadline), 127 not found, any other a failure. `--check`'s rule and the stderr note read it; `main()`'s `shutil.which('lsblk')`, its separate "lsblk not found" note, and `get_macos_diskutil_info()`'s `failed` list are gone. A missing or failing command now counts in `--check` as a stopped one did: a healthy run exits 3 where 1.63 gave 0 when macOS's `mount` fails, and with a pattern (not `-D`) when `lsblk` or `diskutil` is missing or fails; the note says "not found" or "failed (exit N)". `diskutil` and `mount` are found in the sbin directories too. 1.63's other half, "a filter drops a row only on a value that was read", is finished in the same version: a sysfs size or stat that cannot be read, and macOS's throughput, are None, not 0, so the row stays with the cell blank (`null` in `-J`); `-A` drops only a device read as idle, keeps the `-P` rows, and keeps a mount that failed. The record and the note exist only when a collected column needs the command (`lsblk`: FSTYPE, UUID, MODEL or SERIAL, or `-F`), except macOS's `mount`, which is always read and always recorded; `-F`, `-A` and the size filters keep a row whose value was not read, while a pattern is matched against what was read.
- Why we had to change: 1.62 learned to read the exit status of the commands whose output fills the table, but only for one status, 124. A missing `lsblk` was found by a separate `which()` in `main()` with its own note and its own rule (shown columns only: an `-o` without FSTYPE hid it, even with `-F`); a failing `diskutil` went to a third list that only `-F` read; a failing macOS `mount` was not recorded at all. Each was a way not to answer that the check did not see: `statblk --check ext4` on a host without `lsblk` exited 0 over a failing disk whose only `ext4` came from `lsblk`, and on macOS a `mount` that failed (or was not found, as under cron, whose `PATH` lacks `/sbin`) exited 0 over a full filesystem.
- Original design was wrong because: the record was named for one cause ("cut") and each new cause got its own path, so every reader had to know every path, and none did. The causes differ only in the sentence on stderr; what they leave unread, and so what the check cannot tell, is the same.
- Lesson: record "did not answer" once, at the read, with the source's own status, and derive every consequence (rows kept, an unknown exit, the note's wording) from that record; a value from a source that did not answer is "not read", never 0 (its cell is blank).

## 2026-11-23 statblk 1.65: a check left nothing to judge could not tell
- Changed: `--check` exits 3, with a line on stderr that says why (`Nothing was checked: ...`), when it judged nothing: `-x` leaves out both FSUSE% and SMART (which is also the only way to be left no valid output field), or the table has no data row. `nothing_to_check()` reads the table `get_drives_info()` returned (header first) and names the filters in use (`-v`, a pattern, a `-D` pattern, `-M`, `-F`, `-A`) or, with none, says that no block device is listed or shown; `main()` reads it where it decides the exit, and a run that exits 3 this way names the commands that did not answer, as any run that exits 3 does. That covers `-v` with no pattern or one that matches every row (`-v ''`, which is what a script's `-v "$SKIP"` gives with SKIP empty; `-v '.*'`; `-v .` and `-v '.+'`, which match NAME, never blank), a pattern that matches nothing on this host (a typo, a disk that is gone: 1.64 exited 0), `-M` with nothing mounted, `-A` with every device idle, and a host whose `/sys/class/block` lists no device or cannot be read, or lists only a whole disk of size zero (with `-P` the mounts of pseudo and network filesystems that have blocks are rows). What it does not cover: a row whose checked cells are both blank (an unmounted loop, zram or device-mapper device, which has no SMART) counts as healthy, so a host that lists only such rows exits 0 with nothing judged; 1.66 (docs/limitations.md). `-j` and `-J` print what a healthy run prints (`-j` the header row, `-J` `[]`; `[]` for `-j` too when `-x` and `-o` leave no valid output field).
- Why we had to change: found by second opinions on 1.64's final review: `statblk --check -v` and `statblk --check -x FSUSE%,SMART -o foo` exited 0 with no row printed, which cron and a sweep read as healthy, while no disk had been judged. The first fix counted the patterns; the next asked each pattern whether it matches `''` and `'a'`, which is wrong both ways: `-v '.+'` and `-v .` (NAME is never blank, so they match every row) keep no row and exited 0 over a failing disk, and `-v '^$|a'` can keep rows (any row with no empty cell and no `a`) and exited 3 with a false line.
- Original design was wrong because: `check_rows()` called a run healthy when no row reported a problem or an unknown, so "nothing wrong" and "nothing looked at" got one answer, and the fixes decided "nothing looked at" from the arguments, a second path predicting what the filters would leave, which can only fall behind the first (the 1.63 lesson, again).
- Lesson: a health check says "healthy" only when its table gave it a row and a checked column to judge, and it knows that from the rows it judged, not from what its arguments would leave: no data row, or no checked column, answers "could not tell", with why. A typo in a pattern, a disk that is gone and a host where no device is listed or shown are the same case as an all-matching `-v`: the check judged nothing. 1.65 stops there; a row whose checked cells are both blank still counted as healthy (1.66 settles it, below).

## 2026-11-23 statblk 1.66: a name filter matches the name the operator reads
- Changed: `-D` matches its patterns against the device's names: the device path (`/dev/sda1`), the `/dev/mapper/` path of a device-mapper device, and each without the `/dev/` or `/dev/mapper/` prefix, as `NAME` shows it without `-R` (`sda1`, `dm-0`, `pve-root`). 1.65 searched only the two paths. `device_names()` gives the list; `get_drives_info()` keeps a device when any name matches (with `-v`, when none does).
- Why we had to change: the second opinion on 1.65's last re-review: `statblk -D '^sda$'` printed only the header, and `statblk --check -D '^sda$'` exited 3 (`no row is left to judge after the filters (a -D pattern)`; 1.64 exited 0, over a failing disk too), because no path is `sda`. The help said "device names", the README the path; an operator writes the name the table shows.
- Original design was wrong because: it matched the string the code had at hand (the path it iterates over), not the one the operator reads and types (the NAME column), and the docs described the intent while the code matched another string.
- Lesson: an option that filters by name matches the name as the tool shows it, and keeps every form it matched before, so no pattern that matched stops matching. A wider match is a behaviour change for an inverted filter (`-D -v '^s'` kept every row in 1.65 and now leaves out `sda`): say so in the upgrade note.

## 2026-11-23 statblk 1.66: a check is healthy only where it judged a value
- Changed: `nothing_to_check()` gives a third reason, read from the table as the other two are: the table has rows, but no row holds a value in a checked column (`Nothing was checked: no row holds a value in FSUSE% or SMART.`, or the one column `-x` leaves). That is a host, or a filter, that leaves only devices with no mount and no SMART (unmounted loop, zram or device-mapper devices), or `-x SMART` with nothing mounted. Such a run exits 3, prints what a healthy run prints (`-j` the header row, `-J` `[]`), and names any command that did not answer. A host with disks beside such devices is judged by its disks and exits 0 when they are healthy. A SMART of `STANDBY` (smartctl's answer for a spun-down disk) and an `FSUSE%` of `N/A`, `ERROR` or `TIMEOUT` are values.
- Why we had to change: the second opinion on 1.65's last re-review: a row whose FSUSE% and SMART are both blank counted as healthy, so `statblk --check` on a host whose table held only such rows, or `statblk --check -x SMART` with nothing mounted, exited 0 with nothing printed while no value had been judged.
- Original design was wrong because: `check_rows()` calls a row healthy when it has no problem and no unknown, and a blank SMART is healthy by design (a virtual device has none to read). That is right for the row and wrong for the run: "nothing wrong here" and "nothing here to look at" got one answer, as "nothing wrong" and "nothing looked at" did before 1.65.
- Lesson: a check is healthy only where it judged a value. A blank that means "nothing to check here" is healthy for its row and judges nothing for the run; a run whose rows hold no checked value could not tell, as a run with no row could not.
